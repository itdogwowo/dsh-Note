# Note Sync — 維護 DSH 筆記

這個技能的工作是維護這個 repo 的 `notes/`。

## 先讀這個

**`notes/README.md`** 是慣例的唯一來源（索引、兩種檔案性質、四條寫作規則）。
**每次都先讀它**，不要靠這份技能裡的轉述——那份文件會改，這份技能不會。

---

## 兩種動作，性質完全不同

| 動作 | 目標 | 規則 |
|---|---|---|
| **記錄踩坑** | `notes/pitfalls.md` | **append-only**，加在最後，每條有日期 |
| **更新子系統文件** | `notes/skills.md` 等 | **改寫**，錯了就修，不留舊版 |

### 怎麼判斷該記哪一個

```
這件事是「一個發生過的事件」嗎？
├─ 是 → pitfalls.md
│        例：我以為是 A，結果是 B ／ 某個操作造成了某個後果
└─ 否，是「一直成立的事實」 → 對應的子系統文件
         例：技能目錄有四個 ／ description 上限 500 字
```

**同一件事常常兩個都要**：事實寫進子系統文件，「我當初怎麼誤判的」寫進 `pitfalls.md`。
兩邊互相連結。

---

## A. 記錄踩坑

### 格式（照抄，不要自創）

```markdown
## YYYY-MM-DD — <症狀的一句話>

**症狀**：觀察到什麼。

**當時以為**：一開始的判斷是什麼。

**真正原因**：實際上是什麼。

**怎麼驗證**：具體的指令或步驟，讓下一個人能自己重現這個判斷。

**學到什麼**：可轉移的教訓，或指向哪份文件。
```

### ⚠️「當時以為」不可以省

那一欄的價值就在於——**它正是下一個人會誤判的方向**。
一個事後諸葛的版本（只寫正確答案）沒有用，因為讀者不會在那裡停下來。

### 寫之前先查有沒有重複

```sh
grep -n '<關鍵字>' notes/pitfalls.md
```

同一個坑又踩到的話，**加一條新的**（append-only），
在裡面寫「又踩了一次，這次的差別是…」。**不要改舊的那條。**

---

## B. 更新子系統文件

1. 讀 `notes/README.md` 的索引，找這件事屬於哪一類
2. 讀那份文件，**改寫**對應的段落（不是往後面一直加）
3. 橫跨多份的話，選**最主要**的那份寫，其他用相對連結指過去

### 什麼時候該新增一份文件

索引裡沒有它的位置，**而且它已經有兩個以上的獨立條目**時才開新檔。
只有一條的話先塞進最接近的那份。

---

## 紅線

這個 repo 是**公開的**。提交前一定要：

1. **樣板化** —— 真實路徑寫成 `<你的帳號>`、`<專案>`；公司名寫成 `<公司專案名>`
2. **不放截圖** —— 畫面裡的側邊欄有工作區名稱與完整路徑
3. **提交前掃描**：

   ```sh
   git ls-files -o --exclude-standard \
     | xargs grep -l -E 'C:\\Users\\[A-Za-z0-9]|/Users/[A-Za-z0-9]|/home/[A-Za-z0-9]'
   ```

   ⚠️ **不要用 `git status` 當檔案清單**——它會把 gitignore 掉的也算進來，造成誤報，
   而誤報會讓你開始忽略警告。

4. 注意**大小寫**：`/users/${id}` 這種是 API 路由，不是家目錄。

---

## 收尾

1. 新增檔案時，更新 `notes/README.md` 的索引表
2. 確認內部連結沒有指到不存在的檔案
3. commit，訊息用 `note: <一句話>`
   —— 訊息裡**不要**寫出實際的敏感字串

---

## 不要做的事

- **不要改 `pitfalls.md` 已經寫好的舊條目**（只能 append）
- **不要把官方文件抄進 notes** —— 那只該連過去
- **不要寫沒有驗證方法的斷言** ——「我推論是 X」沒有價值；
  「打這個端點，回 200 就是活的」有價值
- **不要把「推論」寫成「實測」** —— 分清楚實測／推論／官方文件寫的
