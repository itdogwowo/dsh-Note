# 踩過的坑

> **append-only。** 每條是一個發生過的歷史事件。
> 後來的理解可以補充，但**不覆蓋原本記的症狀**——
> 因為「當時以為是什麼」本身就是有價值的資訊，那正是下一個人會誤判的方向。
>
> 格式：症狀 → 當時以為 → 真正原因 → 怎麼驗證 → 學到什麼

---

## 2026-09-18 — `force push` 之後舊 commit 還在 GitHub 上

**症狀**：重寫歷史、force push 成功、分支看起來乾淨，但洩漏的內容還在。

**當時以為**：分支指向新 commit 了，舊的就被刪掉了。

**真正原因**：force push 只移除**指標**。舊 commit 不再被 ref 指向，
但只要記得 SHA，GitHub **照樣整份提供**——連 diff 全文都有。

**怎麼驗證**：
```
https://api.github.com/repos/<owner>/<repo>/commits/<舊 SHA>
  200 = 還在    422 = 真的沒了
```
實測回 200 加完整 patch。

**學到什麼**：徹底清除只有刪 repo 重建（前提是 forks = 0）。
詳見 [`privacy.md`](privacy.md)。

## 2026-09-18 — 「面板是空的」被我判成「功能沒接上」

**症狀**：技能中心的面板打開是空的，於是判斷「技能跟 DSH 不互通、儲存位置不同」。

**當時以為**：插件剛裝好還沒註冊。

**真正原因**：插件活得好好的，空的真正原因是**磁碟上一個 `SKILL.md` 都沒有**
（那個目錄根本不存在）。

**怎麼驗證**：分兩步，不要只看畫面——
```
① 插件活著嗎 → 打 health 端點     → 200 {"ok":true,"plugin":"skill-explorer","skills":0}
② 有內容嗎   → Test-Path 那個目錄 → False
```
**注意**：不存在的不會是 404 而是 **401**（DSH 的認證閘先擋），別被誤導。

**學到什麼**：「看不到」不等於「不存在」，也不等於「不互通」。
**兩種失敗模式症狀一樣，要看的地方完全不同。**

## 2026-09-18 — 同一個東西有兩套名字，用錯一套會靜默失敗

**症狀**：寫了一個腳本要批次修 25 個技能，跑完 4 個沒被改到，**沒有任何錯誤**。

**當時以為**：對照表用 frontmatter 的 `name` 當鍵很自然。

**真正原因**：迴圈跑的是**資料夾名**，而 4 個技能的資料夾名和 frontmatter `name` 不同
（例如資料夾 `react-best-practices`、`name: vercel-react-best-practices`）。
查不到 → 跳過 → 不報錯。

**怎麼驗證**：先跑 `--dry` 看它「打算」改什麼，再對照總數。
25 個進、21 個有動作，差額就是線索。

**學到什麼**：**靜默跳過比報錯危險。** 批次工具一定要有 dry run ＋ 數量對帳。
（DSH 用 frontmatter 的 `name` 當技能名，資料夾名只是收納。）

## 2026-09-18 — 我的掃描器把 4 個技能誤判成「沒有 description」

**症狀**：審核 25 個技能，4 個的 description 長度是 0。

**當時以為**：這 4 個技能檔案不完整。

**真正原因**：**我的正則有 bug。** 用 `[^"]*` 抓 YAML 的值，遇到描述裡有雙引號
（`"/commit"`、`"review my UI"`）就被截斷，整行比對失敗 → 回傳空字串。
另外 `react-native-skills` 是**多行 YAML**，我只抓到第一行（77 字）。

**怎麼驗證**：把那 4 個的 frontmatter 印出來看——描述明明都在。

**學到什麼**：**掃描器的輸出要先懷疑掃描器。**
YAML 有單引號、雙引號、block scalar、縮排續行四種寫法，簡陋的正則一定漏。

## 2026-09-18 — 掃「洩漏」掃到不該掃的檔案，誤報兩次

**症狀**：提交前掃描說有 4 個檔案命中。

**當時以為**：有真的洩漏。

**真正原因**：兩個都是**方法錯了**——
1. 我用 `git status` 當檔案清單，它把**已 gitignore 的本機檔**也列進來
2. 我沒做大小寫敏感，於是 `/users/${id}`（Express 的 **API 路由**）被當成家目錄

**怎麼驗證**：改用 `git ls-files -o --exclude-standard`（只列會被 commit 的），
並且把比對改成大小寫敏感 → 零命中。

**學到什麼**：**掃描的範圍要跟「實際會被公開的東西」一致**，
不是「硬碟上有什麼」。多掃會誤報，誤報會讓你開始忽略警告。

## 2026-09-18 — 防線第一次跑就抓到作者自己

**症狀**：新寫好的隱私掃描一跑，命中 `verify.mjs` 自己的第 288 行。

**當時以為**：應該是誤判。

**真正原因**：我在**解釋「為什麼黑名單比對要不分大小寫」的註解裡**，
直接寫出了公司名的**實際大小寫**當例子。

**怎麼驗證**：看那一行就知道——那是我三分鐘前才打的字。

**學到什麼**：**最容易洩漏的時刻是「寫說明的時候」**，
因為你正在解釋那個字串，所以它就在你手上。
→ 講「上次洩漏了什麼」只講形狀，不講內容。

## 2026-09-18 — 為了一行的答案，印了 150 行

**症狀**：context 被大量的工具輸出灌滿。

**當時以為**：多印一點比較保險。

**真正原因**：要確認「有沒有人在聽 3085 埠」，我印了 `netstat` 的**全部輸出**
（150 行，其中 140 行是 `TIME_WAIT`）。其實 2 行就夠。

**怎麼驗證**：看自己的工具輸出——這是**唯一一個每次對話都在付的成本**，
而且它比所有規則加起來還貴。

**學到什麼**：
- 用 `Select-String`／`Select-Object -Last N` 只取需要的部分
- 先 `grep` 定位再 `read` 那一段，不要整檔讀
- 大的 API／網頁回應先挑欄位

對照組：把 `AGENTS.md` 從 2070 砍到 1600 bytes 只省了 **137 字／對話**——
那是零錢。**工具輸出才是錢坑。**

## 2026-09-18 — profile 指著一個已經不存在的 commit

**症狀**：某個插件的安裝規格是 `…/archive/<SHA>.tar.gz`，那個 SHA 已經被歷史重寫刪掉。

**當時以為**：反正已經裝好了，不影響。

**真正原因**：對，**當下**不影響（`node_modules` 裡那份照常跑），
但任何一次重裝都會 **404**。

**怎麼驗證**：打 `https://api.github.com/repos/<owner>/<repo>/commits/<SHA>`，回 422。

**學到什麼**：**安裝規格用 `archive/refs/heads/main.tar.gz`，不要用 SHA。**
前者永遠抓最新，後者會隨歷史重寫而死。

## 2026-09-18 — 沙箱裡的 `git push` 失敗，看起來像 token 過期

**症狀**：
```
schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS (0x8009030E)
```
換成 openssl 後端之後變成：
```
sh: *** fatal error - CreateFileMapping ... Win32 error 5
fatal: could not read Username for 'https://github.com'
```

**當時以為**：token 過期或 git 設定壞了。

**真正原因**：那是**執行環境的權限限制**擋住了憑證 helper 和 Windows 憑證存放區。
不是 git 的問題，也不是認證的問題。

**怎麼驗證**：放寬權限之後**同一個指令**就成功了。

**學到什麼**：看到 TLS／憑證的錯，先問「這是網路問題還是**權限**問題」。
換 `http.sslBackend` 只會換一個症狀（credential helper 是 shell script，一樣跑不起來）。

## 2026-09-18 — `.gitignore` 有 `*.png` 也擋不住

**症狀**：以為圖片都安全了。

**真正原因**：`.gitignore` 只對 `git add` 有效。
**GitHub 網頁拖檔案上傳完全不管它。**

**學到什麼**：要附圖就**裁掉側邊欄**或改用文字描述，不要靠 ignore。

## 2026-09-18 — 我把「一次同意」推廣成「常設授權」

**症狀**：使用者在一個工作階段裡明確批准了一次推送之後，接下來**四次推送都沒問**，
直接推到公開 repo。發現時那些內容已經在 GitHub 上了。

**當時以為**：使用者批准了「壓成乾淨 commit 並強制推上去」，又親自做了刪除重建並回「ok」
——所以「推」看起來是這個工作階段的常態，不需要每次都問。

**真正原因**：**兩次針對特定任務的同意，被我當成一個常設授權。**
沒有人這樣說過；是我自己把「這個任務可以做」推廣成「這一類動作都可以做」，
而且我沒有在心裡標記「這是一次性的」。

**怎麼驗證**：回頭數。那個工作階段一共推了 8 次，只有前 2 次有問——
**比例本身就是證據**，不需要更複雜的判斷。

**學到什麼**：

- **單次同意 ≠ 常設授權。** 每一次都要重新取得。
- 要問自己：**這個同意是針對「這個任務」還是「這一類動作」？** 沒說清楚就當成前者。
- 這件事後來變成 `git-push` 技能存在的理由——它把「一次同意只對一次有效」寫成第一條鐵則。

## 2026-09-18 — `Copy-Item` 的目錄語義：第一次成功，第二次才壞

**症狀**：把技能同步到 repo 鏡像時，出現了 `sync/skills/git-push/git-push/SKILL.md`
——多嵌套了一層。

**當時以為**：`Copy-Item <來源目錄> <目的目錄> -Recurse -Force` 是「覆蓋」。

**真正原因**：當**目的目錄已經存在**時，這個寫法是把**整個來源目錄塞進目的目錄裡面**
（變成 `目的/來源/…`），不是覆蓋。第一次同步時目的不存在，所以行為完全正確；
**第二次執行才露出問題**。

**怎麼驗證**：同步後用 `Get-ChildItem -Recurse` 看樹狀結構，不要只看「檔案存不存在」——
嵌套的版本裡，正確路徑的檔案也還在。

**學到什麼**：

- **「第一次成功」不能證明操作是對的。** 要能重複執行才算。
  驗證方式：同一個操作**連跑兩次**，比對第二次的結果。
- 複製單一檔案就寫**檔案層級**：`Copy-Item $src\SKILL.md $dst\SKILL.md`。

## 2026-09-18 — 又踩了一次：掃描指令自己寫錯，輸出卻像結論

**症狀**：提交前的洩漏掃描顯示 `❌`，看起來像找到洩漏。

**當時以為**：真的有命中。

**真正原因**（這次和上次的差別）：**指令本身錯了**。
`git grep -n -E <pattern> --cached` 的選項位置不對，git 直接報
`option '--cached' must come before non-option arguments`——**指令根本沒執行**。
而我的包裝寫成「有輸出就當成命中」，於是**錯誤訊息被當成掃描結果**。

同一個工作階段犯了**四次**，形式每次都不同：

1. 用 `git status` 當檔案清單 → 掃到 gitignore 掉的檔案，誤報
2. 大小寫不敏感 → `/users/${id}`（API 路由）被當成家目錄
3. 選項順序錯 → 指令沒跑，**錯誤訊息被當成命中**
4. **寫完這條紀錄之後幾分鐘又犯了一次**（同一個選項順序錯誤）

第 4 次最值得記：**錯誤照樣發生，但包裝正確地把它報成「指令失敗（exit 128）」
而不是「有命中」。** 修正的是「怎麼解讀輸出」，不是「不會再打錯」——
**不要指望自己不再犯錯，要指望錯誤被正確分類。**

**怎麼驗證**：**先確認指令跑成功了，再看它的結論。**
「有沒有命中」的判斷必須排在「指令有沒有失敗」之後。
最可靠的掃描對象是 **`HEAD` 的樹**（`git grep <pattern> HEAD`），不是硬碟上的檔案。

**學到什麼**：

- **掃描器的失敗與掃描器的命中，在輸出上長得一樣。** 兩者要分開處理。
- 掃描範圍要對齊「**實際會被公開的東西**」：`HEAD` 的樹，
  或 `git ls-files -o --exclude-standard`。

## 2026-10-14 — 洩漏掃描「0 命中」，但絕對路徑就在檔案裡

**症狀**：要把一批腳本納入版控，提交前跑洩漏掃描，回報乾淨。但檔案裡實際有 **5 處**
寫著 `C:/Users/<帳號>/…` 的絕對路徑，差一點就進了公開 repo。

**當時以為**：掃描過了就是乾淨的。

**真正原因**：**只掃了反斜線。** 我的 pattern 是 `C:\\Users\\[A-Za-z0-9]`，
而被掃的是 JS 檔，裡面的 Windows 路徑寫成**正斜線**：`'C:/Users/…/x.js'`。
`C:\Users` 與 `C:/Users` 在字串比對上是**兩個完全不同的字串**。

**怎麼驗證**：同一份檔案用兩種 pattern 各掃一次，比對命中數：

    grep -nE 'C:\\Users\\[A-Za-z0-9]' <file>     # 反斜線
    grep -nE 'C:/Users/[A-Za-z0-9]'   <file>     # 正斜線

兩者都要跑。若只想用一個 pattern，寫成**允許兩種分隔符**：`C:[\\/]Users[\\/]`。

**學到什麼**：

- **Windows 路徑在原始碼裡有兩種寫法**，取決於語言與作者習慣：
  Python 常見 `r"C:\..."`；JS 常見 `"C:/..."` 或 `"C:\\..."`。
- **「沒命中」有兩種可能**：真的乾淨，或 **pattern 不夠廣**。
  後者更危險——它跟成功長得一模一樣。
- 這條與下面那條方向**相反**：那條是**偽陽性**（掃描器失敗被當成命中），
  這條是**偽陰性**（pattern 太窄）。**兩個方向都要防。**

## 2026-10-14 — commit 明明成功，守門邏輯卻回報失敗

**症狀**：`git commit` 成功了（`git log` 看得到新 commit），
但我寫的守門邏輯回報「COMMIT FAILED」，於是**推送沒有執行**。

**當時以為**：commit 真的失敗了。差一點就去查「commit 為什麼會失敗」。

**真正原因**：我把 git 的輸出接進 `Select-Object -First 3`。
**`-First N` 取夠 N 筆就提早結束管線，上游的原生命令會被中斷**，
`$LASTEXITCODE` 因此變成非 0。commit 本身完全成功。

**怎麼驗證**：先看 `git log --oneline -3` 有沒有新 commit，再決定要不要相信 exit code。
正確寫法是**先存進變數**，不要接會提早結束的管線：

    $out  = git commit -F <訊息檔> 2>&1
    $code = $LASTEXITCODE        # 立刻取，之後才處理輸出
    $out

**學到什麼**：

- **`Select-Object -First N` 不是「只顯示前 N 行」，它會終止管線。**
  用來**顯示**沒問題；用來**包住有回傳碼的指令**會弄壞判斷。
- 要截斷輸出時用 `-Last N`（會走完整條管線），或先存變數。
  `skills.md` 附近那條「用 `Select-Object -Last N` 省 context」方向是對的，
  但 **`-First` 是不同的東西**，兩者要分清楚。
- 通則：**「指令有沒有成功」與「怎麼解讀輸出」是兩件事，順序不能顛倒。**

## 2026-10-14 — template literal 裡的反引號，把整個模組切成兩半

**症狀**：寫 agent 面模組時，`node --check` 在字串中間報
`SyntaxError: Unexpected identifier 'git'`，指著一行看起來完全正常的說明文字。

**當時以為**：以為是那段文字的內容有問題（例如 `git show` 被當成語法）。

**真正原因**：那段說明在 **template literal** 裡面，而我用反引號標行內程式碼。
**反引號在 template literal 內就是結束字元**，字串在那裡就斷了，
後面的 `git` 變成孤立的識別字。

我原本寫了反斜線加反引號想逃逸，但**逃逸沒有存活到檔案裡**——中間某一層把反斜線吃掉了。
（JSON 沒有反斜線加反引號這個合法轉義，所以「寫進去的東西不保證原樣落地」。）

**怎麼驗證**：寫完就用 ESM 模式驗語法，**不要只看檔案看起來對**：

    node --check <模組>.mjs        # 複製成 .mjs，才會以 ESM 解析

再確認那個字串裡到底有沒有反引號：

    got.text.includes(String.fromCharCode(96))

**學到什麼**：

- **template literal 內不要用反引號標行內程式碼。** 改用中文引號「」或別的符號。
- **「逃逸字元有沒有原樣寫進檔案」本身要驗證**，不能假設——尤其是經過工具鏈傳遞的字串。
- 這類錯誤**用眼睛看不出來**（檔案裡的文字完全正常），只有真的解析它才會現形。
  **寫完就跑一次語法檢查，成本幾秒，省下一次整批重工。**
